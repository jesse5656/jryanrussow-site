# Source and Claim Protocol

## Source priority

### Tier 1 — Primary authoritative
- license files;
- official source repositories;
- official release notes;
- official security advisories;
- official project/foundation/vendor documentation.

### Tier 2 — Direct implementation evidence
- named customer case studies;
- implementation-partner case studies with sufficient technical detail;
- conference presentations by implementers/users.

### Tier 3 — Independent technical evidence
- reputable technical reporting;
- package/repository ecosystem evidence;
- credible security databases and advisories.

### Tier 4 — Community supporting evidence
- mailing lists;
- issue discussions;
- forums;
- user reports.

Tier 4 may identify a risk or lead, but material conclusions should be corroborated when practical.

## Required distinctions

Always distinguish:
- software license cost;
- optional hosting;
- optional support;
- optional consulting/training;
- proprietary vendor modules;
- third-party paid modules;
- open-source extensions;
- custom-code maintenance.

## Current-state claims

For time-sensitive claims, record the evaluation date and exact applicable version/branch.

Do not use an old case study as proof of current deployment unless current use is independently established.

## Negative-result discipline

Failure to find evidence is not proof of absence.

Use `UNKNOWN` when evidence is materially insufficient.

## Contradictions

When marketing claims conflict with license text, repository evidence, or feature documentation, authoritative technical/legal evidence controls and the contradiction must be recorded.
